02 · Arsitektur

Pemisahan tugas mengecilkan blast radius.

Scheduler menentukan apa yang due; worker mengerjakan HTTP. Keduanya tidak saling menahan ketika endpoint lambat.

03 · Reliability controls

Enam lapis pertahanan yang sudah nyata di code.

Reliability datang dari rangkaian kontrol kecil yang saling menutup failure window.

01 Duplicate guard

Unique materialization

Satu occurrence Schedule memiliki materialization_key unik. Dispatcher ganda tidak menghasilkan dua Run untuk waktu yang sama.

02 Atomic state

Worker claim

Transisi queued → running memakai conditional update. Hanya satu worker yang menang; payload duplikat menjadi no-op.

03 Overlap guard

Satu running slot

prevent_overlap memakai slot atomik per Schedule sehingga run baru bisa di-skip saat proses sebelumnya masih berjalan.

04 Dual-write recovery

Queued reconciler

Jika Run sudah commit ke MySQL tetapi belum masuk Redis, reconciler memublikasikan ulang Run tanpa queue ID.

05 Hang recovery

Execution deadline

Run yang melewati deadline ditandai gagal dan overlap slot dilepas. Sistem tidak membiarkan state running menggantung selamanya.

06 Safe retry posture

Manual business retry

tries=1 mencegah HTTP side-effect diulang otomatis. Retry dilakukan eksplisit sebagai Run baru dan tetap dapat diaudit.

05 · Trade-off

Dua alur, dua tempat menunggu yang berbeda.

Direct HTTP menahan pekerjaan di dalam satu batch process. Redis Queue menyimpan pekerjaan sebagai payload durable sampai worker siap.

Direct HTTP

Dispatcher sekaligus menjadi executor batch.

One process path
01 Cron + Laravel SchedulerTrigger setiap menit trigger
02 Dispatcher membuat seluruh RunQuery due, lock, advance next_run_at MySQL
03 Bounded concurrency poolJob menunggu slot di memory process wait here
04 Client AClient BClient C HTTP × C
05 Callback menyimpan setiap hasilSucceeded, failed, skipped, duration MySQL
Failure radius Process batch mati → beberapa request in-flight dapat menjadi ambigu sekaligus.

Redis + Horizon

Dispatcher dan executor dipisahkan oleh queue.

Durable worker path
01 Cron + Laravel SchedulerTrigger setiap menit trigger
02 Dispatcher commit RunMySQL authoritative, lalu publish run_id MySQL
03 Redis Queue menyimpan backlogJob menunggu secara durable dan terlihat wait here
04 Worker 1Worker 2Worker N Horizon
05 Setiap worker HTTP + simpan hasilSatu lifecycle dan failure boundary per Run HTTP + DB
Failure radius Satu worker mati → umumnya hanya satu Run ambigu; job lain tetap diproses worker lain.
Alternatif

Direct concurrent HTTP

  • StartDapat membuka banyak koneksi dalam jarak sangat dekat.
  • FailureSatu process crash dapat memengaruhi seluruh batch in-flight.
  • BackpressureBounded pool, chunking, dan recovery harus dibuat sendiri.
  • DeployBatch panjang perlu graceful shutdown khusus.
  • Cocok jikaJob cepat, stabil, I/O-bound, dan peak kecil/prediktif.

Pros

  • Fan-out dapat dimulai sangat rapat jika pool sebesar jumlah Client.
  • Lebih sedikit PHP process dan koneksi database simultan.
  • Tidak membutuhkan broker untuk jalur eksekusi HTTP.
  • Concurrency limit dikontrol langsung di satu executor.

Cons

  • Fatal error atau restart dapat memengaruhi satu batch sekaligus.
  • Recovery partial batch dan request ambigu lebih sulit.
  • Backpressure, metrics, dan graceful deploy harus dibangun sendiri.
  • Run Now tetap membutuhkan background execution agar UI tidak timeout.
Pilih bila: peak kecil dan prediktif, response cepat, kebutuhan start sangat rapat, serta tim siap memiliki custom recovery executor.
Rekomendasi

Redis Queue + Horizon

  • StartBergantung worker warm; dapat dituning per queue dan SLA.
  • FailureWorker crash umumnya mengisolasi satu Run.
  • BackpressureBacklog ditahan sebagai payload durable, bukan koneksi terbuka.
  • DeployGraceful worker termination dan pending job tetap tersimpan.
  • Cocok jikaBurst, durasi bervariasi, audit dan recovery penting.

Pros

  • Backlog tersimpan dan concurrency tidak membanjiri endpoint.
  • Kegagalan worker terisolasi pada satu Run.
  • Recovery, graceful deployment, dan scale-out lebih matang.
  • Queue wait, throughput, worker status, dan job lifecycle terlihat.

Cons

  • Job menunggu jika worker aktif lebih sedikit dari burst.
  • Autoscaling bertahap dapat menambah start lag.
  • Redis, Horizon, Supervisor, dan worker memakai resource operasional.
  • MySQL→Redis adalah dual-write boundary yang membutuhkan reconciler.
Pilih bila: workload bursty atau variatif, audit dan recovery penting, dan SLA dapat dipenuhi melalui warm worker serta pemisahan queue.
06 · Timing reality

Queue bukan bottleneck. Kapasitas worker-lah yang menentukan.

Broker hanya tempat menunggu. Waktu selesai terutama ditentukan peak job, durasi HTTP, dan concurrency yang tersedia.

⌈ N / C ⌉ × T Estimasi durasi batch + overhead

Peak 123 job ≠ 123 worker

Dengan maksimal 10 worker, peak 123 job membutuhkan sedikitnya 13 gelombang. Itu aman untuk resource, tetapi belum tentu memenuhi SLA start ketat. Solusinya bukan otomatis menghapus queue—melainkan ukur durasi, kelompokkan workload, siapkan worker warm, dan stagger job noncritical.

2 worker warm scale hingga 10 sisa gelombang

08 · Reliability boundary

Yang tidak boleh kita janjikan.

Mengakui batas desain justru memperkuat keputusan, karena mitigasinya menjadi eksplisit.

No exactly-once HTTP

Ambiguous failure tetap ada

Jika endpoint menerima request lalu worker mati sebelum hasil tersimpan, scheduler tidak tahu apakah aman mengulang. Side-effect membutuhkan idempotency key di endpoint Client.

No hard real-time

“Bersamaan” perlu SLA

OS scheduling, DNS, TCP/TLS, network, dan latency endpoint membuat start persis bersamaan tidak realistis. Gunakan p95/p99 start_lag.

Single VPS ≠ HA

Recoverable belum high availability

Jika semua komponen berada pada satu VPS, host failure menghentikan sistem. Recovery bisa baik, tetapi HA butuh pemisahan node dan target RTO/RPO.

Redis is operational state

Persistence wajib benar

AOF/RDB, noeviction, disk monitoring, serta backup/restore harus diverifikasi. Queue reliable hanya jika broker juga dioperasikan secara reliable.

10 · Rekomendasi keputusan

Pertahankan fondasi queue. Perbaiki topology. Buktikan dengan test.

Menghapus queue hanya untuk mengejar near-simultaneous start akan memindahkan buffering, recovery, partial failure, dan observability ke custom batch executor. Perubahan yang lebih aman adalah mempertahankan Redis + Horizon lalu memberi jalur khusus untuk workload yang benar-benar time-critical.

MySQL + Redis Queue + Horizon tetap menjadi execution platform.
